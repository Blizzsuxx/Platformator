## Correctness

- [x] **1. Make component attachment exception-safe.** Start in `engine/include/platformator/gameobject.h` (`addComponent<T>`), `engine/src/core/gameobject.cpp` (`attachComponent`, `addComponentInternal`), and `engine/src/core/gamemanager.cpp` (`notifyComponentAdded`). Inspection found that the object publishes its component pointer before registration finishes, while the templated caller still owns it. An exception can leave a dangling slot and, during replacement, an already-retired predecessor. Define the ownership transfer point for both overloads. Cover slot assignment, identity registration, reconciliation, and collider/rigidbody links. Inject failures into first attachment and replacement. Verify the previous state is usable, a retry registers exactly once, and teardown succeeds. Use the existing allocation-failure tests as a pattern.
- [x] **2. Restore batch/direct sprite parity.** Start in `engine/src/rendering/sdlwindowsprites.cpp` and `spriterendergeometry.h`. Intersect source rectangles with the texture bounds before computing UVs, preserve the destination, and skip empty intersections. Share the blend-promotion decision so a default sprite respects caller-supplied texture blend state. Retain promotion for translucent sprite tint and restore shared texture state after drawing. Add direct-versus-batched pixel assertions in `engine/tests/sprite_tinting_test.cpp`. On a 16-pixel red/green texture, a source starting at x=20 must leave the backdrop untouched, and one spanning x=12 to 24 must display the clipped green region. On white, a default sprite drawing red with texture alpha 128 and `SDL_BLENDMODE_NONE` must match the direct red pixel. Include an in-bounds control and a sibling sharing the same texture. Both culling modes use the batch path, so use `Camera::render` as the independent comparison.
- [x] **3. Give the root-returning scene loader synchronous semantics.** In `engine/src/scene/scene.cpp`, guard `Scene::loadScene()` before submitting the transition. This overload requires an idle runtime and returns the incoming scene’s borrowed roots. Callbacks can use `Runtime::requestLoadScene()`. The review observed the old root returned during a step and its handle expired immediately after commit. Test idle success, rejection from a callback without queuing a transition, and explicit deferred loading that preserves the outgoing scene through the callback. Update the public API comment and migration note.

The `transform_setter_probe.cpp` fixture also uses split stepping. Preserve its measurement boundary or explicitly revise its workload identity. Once callers migrate, remove unused modes and share substep orchestration where scalar, SIMD, and colored traversal order and synchronization are preserved.
- [x] **9. Avoid full-population solver bookkeeping on contact-free steps.** Inspect `stepDynamics()` in `physicssolver.cpp` and `commitMovedBodies()` in `physicsmanager.cpp`. The integrated flags are cleared for every registered body, including static bodies. A body leaving its last island must integrate fresh forces and movement on the following step. Simply skipping the clear can reuse stale deltas, and disabling solver deltas also changes the force path. Test contact loss, free-moving dynamics, and registration-slot reuse before comparing work in a mostly static world.

## Outcome & Verification (base revision `8d51ff35` + working tree)

- **Engine test suite (`build/test-make`)**: 37/37 passed (`ctest --test-dir build/test-make -E platformator_package_smoke --output-on-failure`), including fixed `CloneResolutionFailure::clone()` override in `engine/tests/runtime_template_test.cpp` so rollback on published clone resolution is actually exercised.
- **Package smoke (`build/test-make`)**: `platformator_package_smoke` passed (1/1, 54.17 s), verifying installed SDK, relocated consumer, source consumer, and installed `mario` example.
- **Task 12 exploratory pilot (`capture_linear_render.py`, default pilot: 3 reps, 5 warmup, 30 measured, 10,000 sprites, `constant-density-spread`, software renderer, `vsync=1`, output `build/linear-render-pan-pilot/report.json`)**:
  - `camera-stationary`: 30/30 cache hits, 0 population visits, 0 sorts; `visible_selection_ns` mean **0.46–0.58 µs** (median 0.42–0.50 µs), `draw_order_prepare_ns` mean **0.33–0.37 µs** (median 0.28 µs), `render_process_mean_ms` **16.63 ms** (vsync-paced).
  - `camera-motion` (pan): 0 cache hits, 300,000 full-population visits, 0 bounds refreshes, 26 visible-membership changes, 26 sorts (1,442 entries, 7,002 comparisons); `visible_selection_ns` mean **73.9–79.0 µs** (median 67.5–68.5 µs), `draw_order_prepare_ns` mean **2.23–2.56 µs** (median 2.25–2.46 µs), `render_process_mean_ms` **16.62 ms** (vsync-paced).
  - **Outcome**: Selection is ~32× more expensive than draw-order sorting during pan, yet combined CPU cost at 10k sprites is ~0.08 ms/frame. Keep the current cached-linear implementation; if optimizing pan at much larger sprite counts later, target selection (not draw-order sorting).
