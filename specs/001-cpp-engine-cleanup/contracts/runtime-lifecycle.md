# Contract: Runtime Lifecycle and Public References

This contract describes intended cleanup behavior, not guarantees of the current implementation. Preserve familiar public entry points where safe; document the changes below in the README and example migration notes.

## Scene API

| Operation | Idle host call | Call during an ordinary engine callback |
| --- | --- | --- |
| `loadScene(path)` / existing Scene overload | Prepare and commit replacement synchronously | Queue replacement; commit at end-step boundary |
| `clearScene()` | Commit an empty scene synchronously, without running a frame | Queue clear |
| New `requestLoadScene(path)` | Queue the request for the next step boundary | Queue replacement |
| New `requestClearScene()` | Queue the request for the next step boundary | Queue clear |
| `saveScene(path)` | Save current committed scene atomically | Outside supported callback mutation contract; fail at the API boundary |
| `saveScene()` | Save to last successfully loaded/saved path | Same restriction |

One active scene is supported. `loadScene` replaces; it does not append. The last request submitted before the end-step latch wins, so superseded paths are not loaded. Old-scene ordinary callbacks finish that step unless individually disabled/retired. New behavior starts run at the start of the following step. A clear leaves no camera and no default save path; rendering an empty scene is supported. Loading creates the normal fallback camera only if the committed scene has none.

The boundary prepares the selected replacement before retiring old objects. Missing files, malformed schema, duplicate/nonnegative-ID violations, invalid numeric fields, missing required references/assets, wrong reference subtype, and unknown behaviors are load errors. Scene-local IDs may repeat across replacement scenes but are unique across objects/components within one scene; zero is allowed. Staged behaviors resolve against staged objects/resources using an explicit resolver, never by temporarily substituting the active runtime.

Load errors before commit preserve old ownership, lookup maps, and current path. In deferred calls, the error is raised from `simulateFrame`, a stepping wrapper, or `run`, not synchronously from the requesting callback. This does not roll back ordinary game-state edits already made by callbacks earlier in that step. Pending ordinary retirements are made safe before the exception escapes. Callback authors needing synchronous load/error handling use the idle host path.

Scene requests generated by retirement collision callbacks are for the next step. They cannot cause recursive scene changes within the current commit. `onDestroy` and shutdown cannot request structural work, including scene changes, creation/destruction, reparenting, activation, or component replacement. They may inspect their own still-live component state and release retained resources. This restriction is checked once at the centralized mutation boundary, not by scattered object null guards.

## Creation, activation, and retirement

- Object/component creation during a callback returns a borrowed pointer to an owned allocation. Component slots reflect requested attachment/removal immediately; system registration and callback eligibility change at the barrier. The replaced/removed allocation remains physically alive until its users retire, but it is no longer discoverable through the old getComponent slot. During onDestroy, getComponent sees the components still attached at invocation, including a replacement if one was attached.
- A new/replacement ScriptComponent or behavior never joins a dispatch list already in progress. It starts at the next eligible start phase, before any fixed/update/late/collision callback for that behavior.
- Destroy is terminal and idempotent. It marks a subtree/components ineligible immediately; the current callback returns normally and later ordinary callbacks are suppressed. There is no physical deletion inside the callback. After the current behavior returns, remaining behaviors in the same ScriptComponent and later phases skip a retired owner/component; eligibility is not checked only once at the outer ScriptComponent loop.
- Disable suppresses later ordinary callbacks immediately. Re-enable restores eligibility at the boundary. Coalesced toggles produce final desired membership; an off/on pair with no intervening synchronization does not lose a collider or cause spurious exit/enter.
- `onDestroy` is delivered exactly once before an object's component allocations are freed. An intentionally absent component remains absent; the guarantee does not synthesize components removed earlier by game code.
- Registered GameObjects have exactly one runtime owner. Hierarchy links do not delete already registered children. Reparenting preserves world translation and rejects cycles/mixed-runtime parents at the mutation boundary.
- The engine drains retirement-related physics users and eligible collision exits while necessary allocations remain alive, then unregisters, detaches, invalidates, and frees them. When both sides retire, no callbacks target the retired participants.

C++ destructors do storage/resource release only. A centralized lifecycle boundary captures an exception from user destruction callbacks, finishes required cleanup, and then reports it. Arbitrary callback failures during commit do not promise rollback to the old scene; the transactional guarantee covers preparation errors before commit.

## Reference API

`ObjectReference<T>` represents an optional persistent runtime identity, not ownership. `get`/boolean conversion return empty for retired or expired targets. They do not dereference a cached target to discover its identity. Unbound file-ID references, absence of an active Runtime, and references surviving Runtime destruction all produce empty get/boolean results. Bound access uses a slot/generation/runtimeSerial check and requires published live state. Staged handles are accessible only through the build resolver before publication. Type checks happen on binding, including GameObject versus components and BoxCollider versus CircleCollider.

`operator->` and `operator*` require a valid reference; use debug assertions for this programmer precondition. Internal code with established lifetime/type invariants uses borrowed pointers rather than repeatedly resolving the same handle inside pair/solver loops. A returned pointer may be borrowed through its current callback/step scope but cannot be retained across retirement barriers as an unchecked lifetime guarantee.

References deserialize as scene-local IDs, bind through `ReferenceResolver`, and serialize to same-scene file IDs. Expired references save as null. A non-null reference to an object outside the saved scene is an error. Old references stay expired after component replacement, scene replacement with repeated IDs, slot reuse, and Runtime recreation.

Explicit resolve(runtime) may bind an unbound file ID against that committed scene with type checking; missing targets return empty. No-argument resolve returns empty if no runtime is active. Resolving an already bound expired reference never rebinds it to a repeated ID; setReferencedId is the explicit way to request a fresh binding. Staged required-reference validation rejects missing non-null targets.

Existing public integer ID lookup remains a lookup in the committed scene and returns a correctly tagged object or empty result. Registered IDs cannot be manually changed with `setId`. Programmatic creation assigns unused IDs without a full-scene search. Name lookup retains existing first-match behavior for duplicate names; names do not become runtime identity.

The behavior serialization macro and `resolveReferences` signature are migrated to accept the explicit resolver. Handwritten overrides must migrate too; this is a documented source-level API change. Existing valid integer-reference JSON files retain their format.

## Threading and errors

The main thread owns Runtime mutation, script callbacks, and SDL rendering. Physics workers operate only within declared per-phase data ownership. This API does not promise arbitrary concurrent runtime mutation.

External file/configuration/input failures throw descriptive exceptions containing the path/field or operation. The stock/benchmark CLI catches errors, prints a concise diagnostic, and exits nonzero. Internal invariants use assertions and concrete state, not silent skipping. Expected absence (optional component, no camera, expired optional reference) is represented explicitly and checked where it is used.

External asset-reference objects must be released before their owning Runtime is destroyed; the single-runtime resource ownership precondition is documented. Components and staged loads retain resources correctly within that lifetime. Physics-only mode does not acquire video/audio devices. No second active Runtime is supported in this feature.
