# Validation and Evidence Contract

This is a plan for future execution. No benchmark, source removal, safety result, graphical comparison or performance improvement has been established during planning.

## Provenance and comparable baselines

1. Before production edits, record HEAD, actual branch, dirty/staged/untracked status, diff, relevant source/fixture hashes, compiler/build flags, dependencies, OS/hardware, available cores/affinity and working-tree inputs. Freeze an isolated baseline source snapshot **including the exact common characterization fixtures**, not just `git archive HEAD` when uncommitted inputs exist. Keep baseline and candidate source/build outputs separate. Record any snapshot without Git metadata as such rather than reporting a fabricated commit/clean status.
2. Run the same behavior fixtures against the baseline and candidate under equivalent options. Establish and document existing failures, skips or host limitations; preserve them in reports and do not normalize away a new regression. Run enabled sanitizer attempts before any separately reported diagnostic retry with relaxed options.
3. Final timing uses Release, benchmark instrumentation only, `PLATFORMATOR_ENABLE_DEBUG_TOOLS=OFF`, `PLATFORMATOR_ENABLE_WORK_PROBES=OFF`, and no sanitizers. Finish builds and correctness runs before timing. Follow [benchmark methodology](../../../benchmark/README.md), retain manifests and all raw samples; independently pin allowed CPUs, record actual affinity and do not reuse historical hardcoded masks.

## Correctness gates

- Re-audit all C01–C14, including call paths, tests/benchmarks, examples and installed declarations. Final inventory identifies what was removed or retained and why; an unverified hypothetical caller is not a substitute for concrete evidence.
- Run the full applicable normal CTest suite, including individual public-header checks and `platformator_package_smoke`, with debug tools enabled; build/test debug-tools-off production configuration. Run matching baseline/candidate relevant tests, compare failure/skip lists, and explicitly report environment-specific failures. The package smoke's nested consumer builds are not sanitizer evidence.
- Preserve coverage for multi-cell witness survival/final removal/re-entry; candidate-vs-contact transitions; response/support and scalar/block contact behavior; warm-start feature remapping; sleep/wake; callback mutation/destruction; parent/child updates; scene loading; clock cap; asset errors/fallbacks; Audio lifecycle and transient playback. Existing `collider_pair_cleanup_test` checks multi-cell behavior but is not established across multiple workers, while `physics_bookkeeping_test`'s parallel queue case uses triggers. Add a focused behavior-oriented multi-witness one/multiple-worker control with final removal and re-entry if the re-audit confirms the gap; do not test removed implementation details.
- Run affected-work checks in `cleanup-work` for each supported selected worker count, including fixed-peak reuse and quiet work. Run ASan+UBSan and TSan configurations for relevant physics/lifecycle scopes where supported. Preserve output and status; classify unavailable runtimes, known SDL/libdbus lock-order diagnostics or dependency leaks precisely, with baseline comparison. Never represent skipped/unavailable checks as passing.
- Compare actual supported debug overlay output/controls with debug tools enabled using an available graphical smoke or deterministic capture. Since no existing pixel oracle was identified, record the method and result; if graphical execution is unavailable, report output equivalence as unverified instead of inferring it from a successful build.
- Verify public-header compilation, source/installed consumer and Mario package smoke, migration guidance for C02/C03/C04/C12, and unchanged serialized scenes/assets. A retained-API consumer does not prove compatibility for removed methods or stale binaries.

## Workload matrix and interpretation

Run baseline and candidate with the same fixtures, workload parameters, seed, timestep, warmup, measurement steps, process affinity, compiler/dependency versions and instrumentation. At minimum cover:

| Group | Workload | Population/variation | Purpose |
| --- | --- | --- | --- |
| Spatial quiet and movement | `broad_phase` and `broad_phase_stress` | Counts 100/1000 and 50/300 respectively; 1 and 2 or more available workers | Sparse versus dense/skewed occupancy, candidate work and overhead without unrelated tuning changes. |
| Active contacts | `narrow_phase`, `rigid_body_container`, `persistent_contacts` | Counts 10/200, 100/1000 and 10/1000 respectively; stationary and moving/physical contacts; 1 and multiworker | Geometry, solver, sleeping and retained pair populations. Persistent disjoint trigger contacts measure occupancy, not slot churn. |
| Lifecycle and migration | `add_and_remove`, `moving_add_and_remove` | Churn counts 10/100/1000 with steady count 1000; 1 and multiworker | Object churn/moving triggers and complete-step/physics/cleanup costs. Inspect actual candidate counts: object churn alone does not prove pair creation/removal. |
| Targeted pair churn | Existing or minimally added common baseline/candidate fixture with explicit first-witness creation and final-witness removal counts | Small and large populations, multicell witness cases; 1 and multiworker | Isolate C01's affected path. Demonstrate nonzero and expected pair creation/final removal, comparable work, and reproducible snapshots before attributing costs. If a suitable fixture cannot be established, C01 timing remains unverified. |

For correctness, run invariant validation separately (one repetition minimum per group/worker) and retain event/state snapshots; compare controlled serial/multiworker and baseline/candidate scenarios under established tolerances. For unconstrained solved scenes, the maintainer's prior waiver of cross-worker trajectory equality applies: report differences, validate invariants independently, and compare distributions/controlled cases rather than requiring identical contact histories or support totals. Validation instrumentation marks timings ineligible.

For timing, use at least five fresh independent processes per matched group with 120 warmup and 600 measured steps at the same `dt` and seed, unless a documented reason and equivalent revised schedule is recorded. Preserve schedule/order and vary or alternate baseline/candidate order to reduce drift. Report complete-step average and p95, relevant broad/narrow/cleanup scope statistics and between-process variation; nested scopes must not be summed. Document warmup, actual pair/contact counts and comparability for every group. A microbenchmark may diagnose an effect but cannot replace engine-level validation.

Measure `sizeof` and layout of `ColliderPair`, `ClipPointWithData`, `Audio` and `GameObject` for both builds with their own compiler flags, plus retained pair-table capacity/peak population and allocation behavior using suitable separate instrumented probes or equivalent tooling. Where available, collect peak RSS in matched independent child processes with `wait4` or an equivalent isolated process measurement; distinguish process-wide noise from per-pair/vector storage. Absence of a measurable RSS difference is not evidence that fields were not removed. Do not add production instrumentation solely for this measurement without documenting its scope and timing exclusion.

Report results with raw artifacts, source fingerprints, sample counts, correctness eligibility and comparable group-level outcomes. Investigate unexpected changes, including noise, object layout, scheduling, physical state and worker count. Report inconclusive or unavailable comparisons explicitly; no percentage speedup or statistical threshold is assumed by the specification.
