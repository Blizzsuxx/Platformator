# Research: Sprite Z Ordering and Render Culling Cleanup

Date: 2026-11-17. Scope: the feature specification plus the user's explicit preference for KISS, less code, limited defensive checks, and performance. This is source/design research; no runtime speedup has been measured.

## 1. Culling and draw-order ownership

**Decision.** Make cached-linear visibility the normal runtime mode for this change. Retain the render grid for controlled comparison and as an explicit option for large, mostly stationary worlds with sparse views. Keep current-linear and submit-all paths available for correctness controls and fallback. Do not add a population threshold or automatic strategy switch. The indexed mode currently becomes the default when no environment override is supplied; that default is part of the planned cleanup.

For visibility membership, keep a dense unsorted vector of retained window slots with an inverse position on each culling record. Keep an independent contiguous draw-entry vector sorted by (zOrder, registrationSequence). A same-member camera query with clean retained keys reuses both lists. An actual membership change or retained key edit prepares draw order once. A rejected slot's Z edit is skipped by inverse-position lookup; later admission reads its current value. Both cached modes use the existing exact classifier. Only indexed mode owns the spatial grid.

**Rationale.** Current authored scenes inspected contain 22 Mario sprites and 44–66 Crystal Citadel sprites. At these counts cached-linear avoids the grid's maintenance and setup, and its camera-miss population walk is small. The historical 10,000-sprite SDL software pan favors indexed over cached-linear by only 0.022 ms in paired step-plus-render means, while fully moving crossing favors cached-linear by 0.588 ms. Those are separate historical workloads, not a threshold. Population alone cannot select a winner. Static camera frames reuse the cached selection. Camera movement scans bounds in cached-linear, while the grid queries local candidates without refreshing static bounds. The grid's four-link/node capacity per record and dynamic cell migration belong in the cost and resource comparison, not in a claim that every large scene benefits.

**Segmented interval list evaluation.** Do not replace the render grid or cached-linear with the physics AABB/SegmentedIntervalList implementation in this feature. A previous archived render experiment already placed the camera and sprite bounds into a segmented spatial context, queried camera-sprite overlap witnesses, then restored draw order. In its corrected 1,000-sprite moving fixture with 1% initially visible, the one-worker segmented culling phase measured 0.127 ms versus 0.054 ms for linear and 0.071 ms for BVH. At 100% visible, it measured 0.273 ms versus 0.077 ms linear and 0.197 ms BVH. Its complete software-render values showed the same direction for those fixtures. This is evidence against adopting that particular segmented query path by default. It does not prove that the interval-list primitive cannot serve a redesigned render query.

The existing interval list maintains collider endpoint order, crossing events, checkpoint sets and overlap-pair state. Physics and rendering bounds are not interchangeable. Example assets include sprite and collider dimensions that differ, a Cavern spawner without a collider, and Foundry turret-barrel sprites without colliders. Reusing the physics list directly would omit valid sprites or require renderer-specific endpoints and lifecycle ownership. The archived render experiment handled that with separate visibility proxies and a camera endpoint, so it did not reuse gameplay collider membership. A new interval-list camera index would still pay endpoint swaps and overlap maintenance as sprites move, and it would need to produce a visibility set without physics pair bookkeeping.

The 2009 paper identifies segmented interval lists as beneficial for large mostly-static sets with a small number of insertions/removals. Camera visibility is a range query and moving sprite endpoints can cross each other even when both sprites remain outside the view. That workload can generate maintenance that yields no change to the visible set. Evaluate a new interval-list renderer only if the bounded comparison shows the grid and cached scan miss an intended workload, and compare the renderer-only range-query design against the archived camera implementation.

**Alternatives considered.** A dynamic AABB tree fits arbitrary rectangle queries and size distributions but still needs refit/reinsertion and has no result here that justifies adding it. The old archived tree path and segmented path each had tradeoffs in corrected qualification; neither supplies universal evidence over cached-linear. A uniform grid can be effective for similarly sized, spatially distributed sprites, but current implementation pays cell/link maintenance, side-list scanning and capacity costs. Cached-linear is the simpler starting choice for ordinary authored-scale populations. The existing pilot did not time those small populations. With no post-Z code measurements, the mode choice is an evidence-backed starting default, not a claim of universal optimality.

**Sources.** Current mode selection and camera query: engine/src/sdlwindow.cpp; current index storage and capacity: engine/src/renderculling.cpp. Physics interval-list ownership: engine/src/aabb.cpp, engine/src/segmentedintervallist.cpp, and engine/src/localsortarray.cpp. Archived segmented camera implementation and corrected report: [render query at commit a5b9dda5](https://github.com/Blizzsuxx/Platformator/blob/a5b9dda5bcc447ff5080083085180459ef7c68f9/src/renderculling.cpp#L455) and [linear correction results](https://github.com/Blizzsuxx/Platformator/blob/a5b9dda5bcc447ff5080083085180459ef7c68f9/specs/007-integrate-bvh-culling/evidence/linear-correction.md). The archived report identifies its captures as bounded, source-specific and not universal. The original [segmented interval list paper](https://mathweb.ucsd.edu/~sbuss/ResearchWeb/EnhancedSweepPrune/SAP_paper_online.pdf) describes its coherence and insertion/removal scope. Box2D's [dynamic tree documentation](https://box2d.org/documentation/group__tree.html) describes AABB region-query use and node/leaf visit statistics.

## 2. Invalidate against the prepared candidate set

**Decision.** Pass the edited dense slot from a registered Sprite to the window. A valid published subset provides an O(1) membership test. Ignore a rejected slot for this preparation. For an all-sprite preparation every registered edit counts. An invalid order is already scheduled for reconstruction. Build from current authored values when a sprite enters view, when structural identity changes, or when fallback expands the set.

**Rationale.** Repeated offscreen assignments cannot affect compositing among a fixed set of retained sprites. Retaining a sprite conservatively, even if it ultimately contributes no pixels, still makes it a member. This rule uses the exact published membership without a fresh visibility query or a per-edit queue. It also handles edits made before any camera or projection change is observed by the renderer.

**Alternatives considered.** A binary search of the existing published numeric ranks would address offscreen edits in O(log V) if the old culling representation were kept. The inverse position also addresses the separate cost of numeric sorting on a pan. For one retained edit the planned production baseline still rebuilds and sorts. The pilot will test a cheaper alternative that saves the edited entry's previous key, finds it in the sorted list, and repositions it using the final key. Repeated edits to that slot coalesce. A second distinct retained edit, a new candidate set or a structural change uses the full rebuild. Charge the alternative's bookkeeping and shifts to its timings. Keep it only if the comparison justifies that extra state.

## 3. Stable ties belong to the renderer registration lifetime

**Decision:** Assign a monotonically increasing 64-bit sequence at each actual window registration, stored beside the dense sprite slots inside renderer-owned ordering state. Move the final slot's sequence with its sprite on swap removal. Do not store this derived key on `Sprite`, serialize it, or clone it. Invalidate and clear prepared entries before a registration/removal can make cached ranks stale. Reset ordering storage at successful scene-clear/replacement and shutdown boundaries, together with culling storage.

**Rationale:** Headless windows have no ordering-state allocation or change tracking. A moved surviving sprite keeps its key, while a genuinely re-registered sprite gets a new one. The authored `zOrder` remains an ordinary Sprite field in every mode. A 64-bit sequence does not need a runtime rebasing/overflow recovery subsystem for this feature.

**Alternatives considered:** Addresses, storage indexes, and mutable file IDs do not describe stable live registration precedence. Putting an extra sequence on every Sprite simplifies access but initializes renderer-only bookkeeping in renderer-free operation. A map duplicates the existing slot registry.

**Sources:** `GameManager::registerGameObjectSubtree`, `reconcilePending`, scene commit and `shutdown` in `engine/src/gamemanager.cpp`; `engine/src/scenebuilder.cpp`, `engine/src/template.cpp`, `engine/src/gameobjectserializer.cpp`. Current activation reconciliation actually unregisters inactive sprites, so a later activation receives fresh precedence. Offscreen/texture changes alone do not unregister.

## 4. Sequential preparation; no new concurrency infrastructure

**Decision:** Run ordering on the owning render thread after existing worker completion, and keep SDL submission on that thread. Use `std::sort` initially; do not add a parallel threshold, scheduler, locks, atomics, or worker notifications.

**Rationale:** Stable frames have no sorting task. Dirty frames sort only retained candidates, often a small set; a serial pass is the least code and avoids task startup/join and per-sort worker resource costs. Large all-visible, frequently reordered sets are the serial bottleneck to measure. This is a design rationale, not evidence that serial sorting is universally fastest.

**Alternatives considered:** oneTBB `parallel_sort` can partition an immutable entry array with the same total key and join before submission, so it is technically feasible. The vendored implementation already has its own small-input cutoff; do not copy that constant into engine policy. Only a measured hotspot would justify replacing the one sort call and validating allocation and worker scaling. No alternate sorting backend is shipped for speculative use.

**Sources:** `vendored/oneTBB-2022.3.0/include/oneapi/tbb/parallel_sort.h`; [oneTBB parallel_sort documentation](https://uxlfoundation.github.io/oneTBB/main/reference/source/algorithms/functions/parallel_sort_func.html) describes parallel execution and unspecified equal-key order. Our unique registration tie key makes final order independent of sorting stability. [SDL_RenderTextureRotated](https://wiki.libsdl.org/SDL3/SDL_RenderTextureRotated) requires main-thread calls. Worker-equivalence correctness checks and selected existing controls suffice initially; no multicore sorting speedup is claimed.

## 5. Extend existing public/asset boundaries

**Decision:** Add `Sprite::getZOrder()` and `setZOrder(std::int32_t)`, a zero-initialized member, clone copying, and optional legacy-compatible JSON member `zOrder`. The setter returns on equality and otherwise updates the value and notifies the window only for a registered sprite. The notification includes the slot and follows the prepared-set membership rule above. It leaves geometry invalidation untouched. Validate JSON integer type and signed-32 range before narrowing; accept an absent field as zero. Use existing load exceptions and editor validation diagnostics.

**Rationale:** A typed setter cannot receive a wider integer without caller conversion, so it needs no range check, exception wrapper, or silent correction. JSON can contain unsigned values larger than the signed range, booleans, floats, or null; checking the boundary prevents truncation. Internal ranks/owners are established invariants and can use assertions, not repeated defensive resolution in the draw loop.

**Alternatives considered:** Constructor overloads make a small property unnecessarily invasive. Using transform z introduces unrelated geometry semantics. A generic numeric-validation library or new error protocol is unnecessary for one field.

**Sources:** `engine/include/platformator/sprite.h`, `engine/src/sprite.cpp`, `engine/src/spriteserializer.cpp`, `engine/src/inputvalidation.h`; `editor/src/panels/inspector.cpp`, `editor/src/validation.cpp`. The [Unity sortingOrder documentation](https://docs.unity.com/en-us/engine/6000.5/script-reference/unityengine/renderer/sortingorder) confirms the familiar higher-value-in-front direction and documents its narrower range. Platformator deliberately uses its specified full signed-32 domain, local Z Order naming, and no named sorting layers; no Unity tie rule is assumed.

## 6. Editor preview is a separate rendering path

**Decision:** Add the property to existing Inspector integer editing/semantic nodes, component defaults, document change classification, validation/fingerprints, and separately cached preview ordering inputs. Preview manually submits sprites through `Camera::renderWithView`, so it needs its own cached draw-ID vector. Preserve `orderedDocumentIds_` as document order; add stable preview registration precedence and dirty the draw list only on sprite registration/membership or Z Order changes. A false-to-true active transition establishes fresh precedence, matching runtime re-registration; view/texture changes preserve it. Reuse normal image-dirty/update paths.

For viewport overlap picking, preserve non-sprite authoring targets and per-object collider/camera/sprite priorities. Order the sprite-bearing object subsequence by the cached visual sequence before the existing reverse traversal/pick cycle. This reuses the visual list on click; it does not sort each frame or replace the selection system.

**Rationale:** Updating only runtime `SDLWindow` would leave authoring preview incorrect. Updating the preview's document-order vector itself would mix document traversal with visual order. Existing pick-cycle tests assume sprite overlap follows drawing order; the bounded adapter keeps that expectation while retaining other target types.

**Alternatives considered:** Routing preview through runtime window drawing conflicts with its custom camera/target and existing authoring filtering. A generic cross-renderer ordering service adds more machinery than the two short sort sites need. Rebuilding preview ordering on every camera or animation update is unnecessary.

**Sources:** `editor/src/componenttypes.h`, `editor/src/validation.cpp` (including validation fingerprints), `editor/src/editcommands.cpp` (generic Sprite change classification), `editor/src/componentoperations.cpp` and `editor/src/templates.cpp` (generic fields); `editor/src/preview.h/.cpp` (`Proxy::SpriteInputs`, `update_proxy`, `rebuild`, `render_scene`, reset); `editor/src/document.cpp`; `editor/src/viewport.cpp` (`viewport_pick_targets`, `ViewportPickCycle`); `editor/tests/viewport_cases.cpp`.

## 7. Bounded evidence for Z ordering and culling cleanup

**Decision.** Extend the existing guarded render capture driver and probe with a small, selected comparison. Keep its defaults of three independent repetitions, five warmup frames, 30 measured frames, 50 MiB and 600 seconds. Do not form a Cartesian product of every culling mode, ordering strategy and worker count. Reuse the existing build pairs and separate validation/resource probes from uninstrumented timing. Keep complete commands, source/build/workload identities and raw timing samples with a compact report.

The [combined pilot](quickstart.md#5-one-bounded-combined-pilot) defines the executable cases and their controls. For both the 64-sprite all-zero fixture and the 10,000-sprite all-zero sparse pan, compare pre-change indexed, candidate indexed and candidate cached-linear. Holding policy fixed isolates the combined implementation cost. Holding build fixed isolates the policy tradeoff. For 10,000 retained mixed-Z sprites, hold policy at cached-linear and compare rebuilding, per-frame sorting and single-entry repair, with clean and edited frames reported separately.

Fully moving crossing is a work/resource control across the three enabled policies. It diagnoses maintenance and storage without supplying fresh fully-dynamic latency evidence. Rejected-only edits on a prepared cached subset must leave drawing order clean. Pan an edited sprite into view and verify its latest Z on admission. Use targeted tests for mixed-Z pan, bulk edits, fallback and stable-capacity churn.

**Rationale.** Existing pre-Z all-zero probe arguments can establish equivalent controls for the static and pan cases. They do not support explicit Z. Candidate/reference comparisons for explicit order therefore use the same candidate build and fixture. The 64-sprite proxy addresses likely product-scale work without claiming an exact application scene capture. The dense case covers the sort worst case that the previous 1,000-sprite sparse pilot missed. The fully-moving case directly addresses the current grid's unfavorable historical result. Culling policy and Z-sort policy remain independently interpretable.

**Measurement rules.** Verify the resolved sprite positions/size distribution, retained count, edit schedule, camera/output mapping, renderer, workers, seed, source and build identity. Validate output independently before comparing times. Start paired timing before the setter and end after rendering. Record step and render scopes independently. Report separate render and step scopes, complete paired step-plus-render, typical/tail samples, per-process spread, initialization and retained capacity. Do not sum nested scopes. Report draw entries visited, comparisons, moves, membership visits/changes, bounds refreshes, grid links/cells, and allocation/resource observations in the instrumented validation run. Raw per-frame identities or images do not belong in retained artifacts. If a case or requested phase cannot fit within the stated budget, stop and report the partial result.

**Limitations.** Historical grid, segmented and linear measurements come from different commits and fixtures. They explain the proposed cases, not a candidate acceptance result. The archived segmented camera result covers 1,000 sprites and its specific segmented context. The current grid report covers its own implementation and 10,000-sprite workloads. Neither predicts hardware-renderer latency or a universal culling crossover. No Z-order timings have been measured.

**Sources.** Existing case definitions and guards: engine/benchmarks/capture_linear_render.py, engine/benchmarks/linear_render_probe.cpp, engine/benchmarks/tests/test_linear_render.py, AGENTS.md. Historical current-grid comparison: [incremental culling results](../009-incremental-render-culling/evidence/RESULTS.md). Historical segmented camera comparison: [corrected render-index report at commit a5b9dda5](https://github.com/Blizzsuxx/Platformator/blob/a5b9dda5bcc447ff5080083085180459ef7c68f9/specs/007-integrate-bvh-culling/evidence/linear-correction.md).

## Resolution

The research recommends cached-linear as the normal culling default at current authored scale, while retaining indexed culling as a measured option for large sparse worlds. Z ordering uses a separate cached draw list. The historical segmented camera experiment is considered and does not justify adopting that path as the default. The bounded comparisons above must still measure the post-change build before making performance acceptance claims. No new third-party dependency or constitutional exception is proposed.
